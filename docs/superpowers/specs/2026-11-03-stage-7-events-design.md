# Завершение этапа 7: мероприятия

## Основание и границы

Реализовать оставшиеся методы разделов 5.3 и «Этап 7» в
`backend/TECHNICAL_SPECIFICATION.md`. Сохранить существующие `EventsService`,
`EventsController` и `OrganizerEventsController`. Публичный каталог уже реализован;
для отсутствующей или недоступной публичной карточки исправить HTTP 400 на 404.

## API и доступ

- `POST /api/events`: создать DRAFT, HTTP 201, ответ EventItem.
- `PATCH /api/events/:id`: редактировать мероприятие, HTTP 200, ответ EventItem.
- `POST /api/events/:id/publish`: публикация, HTTP 200, ответ EventItem.
- `POST /api/events/:id/cancel`: отмена, HTTP 200, ответ EventItem.
- `GET /api/organizer/events`: список OrganizerEvent, сортировка createdAt desc.
- `GET /api/organizer/events/:id`: одна карточка OrganizerEvent.

Все перечисленные методы доступны ORGANIZER и ADMIN через существующий RolesGuard.
Общая проверка владельца разрешает ORGANIZER доступ только к собственным
мероприятиям, ADMIN — ко всем. Отсутствующее или чужое мероприятие возвращает 404.
Параметры id валидируются как UUID. Маршрут OrganizerEventsController меняется
на `organizer/events`.

## DTO и представление

CreateEventDto использует class-validator: title — 3–120 символов; venue и city —
1–120; description — необязательная строка до 5000; startsAt — ISO8601;
priceCents — целое от 0 до 1000000; capacity — целое от 1 до 100000;
coverImageUrl — необязательный URL или null. UpdateEventDto использует PartialType.
Null не должен проходить для полей, которые не допускают его в модели.

Будущая дата проверяется сервисом при создании, изменении даты черновика и
публикации. Создание устанавливает organizerId текущего пользователя,
availableSeats = capacity и DRAFT. Currency сохраняет значение по умолчанию usd.
Ответы содержат organizer с id и name, без organizerId.

## Редактирование и переходы статусов

DRAFT допускает изменение всех полей DTO; при изменении capacity одновременно
устанавливается availableSeats = capacity. PUBLISHED допускает изменение
описательных полей. Переданные startsAt, priceCents и capacity допустимы только
при совпадении с сохранёнными значениями; иначе HTTP 409 EVENT_LOCKED.
Любой PATCH отменённого мероприятия возвращает HTTP 409 EVENT_LOCKED.

Публикация разрешена только из DRAFT с будущей датой. Отмена разрешена из DRAFT
и PUBLISHED. Недопустимый переход возвращает HTTP 409 INVALID_STATUS_TRANSITION.
Изменения выполняются с условием текущего статуса и проверкой count, чтобы
конкурирующие запросы не обходили ограничения. Редактирование и публикация
должны учитывать конкурентное изменение проверенных полей: проверка и запись
образуют одну согласованную операцию с блокировкой строки в транзакции либо
условной записью по прочитанным значениям с повторной проверкой при конфликте.

Отмена в одной транзакции меняет статус мероприятия и все его PENDING-брони
на CANCELLED с cancelledAt. PAID-брони обрабатываются будущей фоновой задачей
этапа 12. Внешних вызовов в транзакции нет.

## Статистика

Общий метод добавляет stats к одной или нескольким карточкам. Один groupBy
по eventId и status суммирует quantity и totalCents для PAID/PENDING:
paidSeats и revenueCents берутся из PAID, pendingSeats — из PENDING.
Отсутствующие суммы равны нулю. Для пустого списка запрос статистики не нужен.

## Проверка

Добавить тесты создания и валидации, владельца и ADMIN, отсутствующей публичной
карточки, ограничений PATCH, совпадающих защищённых полей, публикации с прошедшей
датой, повторных переходов и атомарной отмены PENDING-броней. Проверить статистику
PAID/PENDING, нулевые суммы и отсутствие N+1. Проверить маршруты и ролевые
ограничения. Запустить подходящие тесты backend, сборку TypeScript и линтер
изменённых файлов. Конкурентные сценарии проверять интеграционно при доступной
тестовой PostgreSQL; ограничения среды указать в результате.
